# Final server security review — 2 November 2026

This review found and fixed two confirmed problems: a mail-queue cancellation/lease race and a malformed-CSRF comparison failure. Six new deterministic local regressions reproduced the failures before the fixes. The focused auth/email/privacy cohort then passed 27 checks; the full server/shared run passed 181 checks. The actual workerd/D1/R2 integration test and TypeScript check also passed. `npm audit --json` reported zero known advisories across 366 dependency records at review time.

Scope: fresh attack hypotheses in authentication/session/role/CSRF handling, private photos/public media, bounded request parsing and output encoding, queue state changes and privacy erasure. Address matching and subscription targeting were assigned to a separate reviewer; their findings must be assessed with this report. The review made no production writes, sent no external messages and performed no commit/deployment. Release baseline reported by the owner was application `e03a452`, documentation `e9ecce0`; the fixes below are local changes for the release owner's combined check.

## Confirmed findings and fixes

| Finding | Reproduction and impact | Fix and evidence |
| --- | --- | --- |
| **FSA01 — privacy cancellation did not invalidate already claimed mail; stale workers could overwrite later state** | `deliverPending` claims a bounded batch before sending its items. A later item remained in the worker's memory when owner erasure cancelled or deleted its outbox row during an earlier send. The old worker still sent that private content. Cancellation while R2 loaded a photo had the same problem. Separately, an in-flight accepted response could overwrite a privacy cancellation; a late 429 could revert a newer successful lease to pending. This requires real concurrent processing/cancellation or overlapping leases; it is not an unauthenticated account-access bypass. It is a material privacy and queue-integrity problem during normal operations. | `server/email.js:84` binds settlements to the original row ID, pending status, lease deadline and attempt counter. The sender rechecks that ownership and current subscription eligibility immediately before dispatch, after waits/photo loading. Cancelled/deleted rows are skipped, and late responses cannot overwrite another state. Five new `server/email.test.mjs` regressions cover cancellation, deletion, photo-loading cancellation, accepted-response cancellation and stale transient-response overlap. They failed before the fix and passed afterward. Existing stable idempotency keys, retry caps/backoff, timeout and retry-window behavior remain. |
| **FSA02 — equal character length did not imply equal byte length for secret comparisons** | A logged-in user's deliberately forged 64-character Latin1 CSRF value had the same JavaScript length as the ASCII token but a different UTF-8 byte length. `timingSafeEqual` threw, producing 503 instead of rejecting 403. No authorization bypass was found; impact was malformed-input handling and misleading availability errors. | `server/admin-auth.js:34` now verifies encoded byte lengths before constant-time comparison. The new `server/admin-auth.test.mjs` test reproduced 503 before the fix, then 403 afterward, verified no account invitation was created and confirmed the legitimate session still worked. |

The new queue check closes the observed waiting/attachment/stale-settlement races. It cannot make an external email send atomic with a database deletion: a send already dispatched after the last eligibility check can still be accepted. Already accepted mail cannot be recalled. The existing owner-facing privacy scope warning remains necessary and unchanged. There is no new resend operation or change to retention/consent policy.

## Boundary review and supporting evidence

| Boundary | What was examined and established |
| --- | --- |
| Authentication and sessions | Password alone does not establish a session. Login requires configured Turnstile, a valid active account/password and a single-use expiring eight-digit email code. Challenge attempts, mail/resend and login limits remain. Codes are stored as peppered digests, cookie values as digests; production cookies use `__Host-`, Secure, HttpOnly, SameSite=Strict and Path=/. Duplicate/malformed cookies are rejected. Current account status/password-version is re-read during authentication; revocation/scope changes invalidate existing credentials as tested. Local auth bypass requires the separate local-storage adapter and loopback host; there is no public code endpoint. |
| Origin, CSRF and roles | Admin mutations require exact Origin and a matching CSRF token; cross-site fetch metadata is rejected. Owner account management/privacy/recipient restrictions and content-versus-operations route guards were reviewed, not replaced with client-only checks. Compatibility default `all` for preexisting editors is an intentional recorded policy, not a newly tightened permission rule. Scope and revocation suites pass. |
| Private citizen photos and public CMS media | Private photo retrieval authenticates and checks operational access before reading the source record; object keys/extensions are constrained and the response has no-store/nosniff/sandbox headers. Anonymous photo guesses and private submission reads remain unavailable. CMS uploads are deliberately public media, separate from report-photo routes: type/size/signature checks, generated keys and sandbox/nosniff responses prevent treating uploaded content as executable application markup. No arbitrary server-side URL fetch from citizen fields was found in these paths. |
| Bucket configuration | The release owner verified **actual production configuration read-only** through successful Cloudflare API calls for `kpv-portal-photos`: managed `r2.dev` access `enabled:false`, custom domains `[]`. No bucket setting was changed. This supplements application-route checks; the report does not rely on unguessable object keys as authorization. |
| Request parsing and state changes | Public JSON, admin JSON/auth JSON and multipart uploads have streamed byte caps; bodies must parse to expected object shapes. Published CMS sections are validated server-side; drafts remain account-scoped. SQL input is parameter-bound, with dynamic table/section choices constrained internally. Public submission retry IDs bind to content/photo digests and atomically create one source record/outbox entry; changed retries conflict. Work treatment and publication use revisions/CAS, preserving original citizen payloads. Existing concurrency tests pass. |
| HTML, links and documents | Public React fields and HTML email details are escaped; no citizen-supplied HTML template evaluation was found. CMS URL/image validation blocks executable schemes, technical/private paths and active formats in the examined validators. Public document responses specify CSP, nosniff, framing, permissions and HTTPS transport headers; admin/subscription documents add no-referrer/no-store/noindex. Preview messaging verifies source window and same origin. Broader URL/address-rule behavior is also covered by the separately assigned frontend/shared review. |
| Capabilities and privacy erasure | Subscription links use purpose-separated signed/versioned capabilities; management and unsubscribe have different read powers. Existing confirmation compatibility is retained; older management versions are revoked on replacement/withdrawal. No capability redesign was made here. Owner erasure requires an HMAC confirmation bound to owner/reference/fingerprint/expiry, rechecks changed records, suppresses subscriber work, cancels pending mail, deletes constrained R2 keys before removing source records and writes only count-based audit evidence. R2 failures preserve retryable records. Existing privacy/capability tests pass; FSA01 additionally strengthens the sender's side of this boundary. |
| Logging and dependencies | Application queue logs contain event/status/reason, not message bodies, credentials or addresses. Repository Wrangler configuration enables query-string redaction; this run did not independently re-read every live logging integration. Dependency audit returned no advisory findings; no dependency upgrade or lockfile change was necessary. |

## Validation and limits

- Added **six meaningful regression cases**, all locally reproduced as failures first: five queue interleavings and one malformed-CSRF case. No real API key, private production backup, live campaign or recipient inbox was used by the tests.
- `node --test server/email.test.mjs server/admin-auth.test.mjs server/privacy.test.mjs`: 27 passed.
- `npm run test:unit`: 181 passed at this review's run. Other agents may add tests before the release owner's final combined check.
- `node --test server/worker-runtime.test.mjs`: 1 passed in actual local workerd with D1/R2 simulation. This reruns a meaningful integration after the queue change; it is already included in the 181 cohort and is not a second unique test count.
- `tsc --noEmit`: passed. `npm audit --json`: 0 known vulnerabilities; this is registry advisory coverage, not a proof that every dependency is defect-free.
- No new live adversarial/load test was performed. Earlier isolated remote-QA results establish their recorded HTTP workflows, but that temporary environment has been removed. These new fixes still require the release owner's build/deployment verification.
- No automated retention period, backup-destruction procedure, delivery webhook or safe manual resend policy was invented. Provider copies, recipient mailboxes, backups and staff-created free-text notes outside a matched case/reference require their own operational handling. The erasure tool intentionally caps one request at 200 submissions/500 deliveries and requires separate handling beyond that limit.
- Password hashes use the established PBKDF2 format and work factor; this pass did not migrate credentials or claim protection against an attacker who controls production secrets/database or a staff member's email/device. Protecting those systems, individual access decisions, official data accuracy and incident/retention policy remain operator responsibilities.
- Production test-data cleanup was separately authorized and assigned to the release owner. It is not part of this agent's changes, and no deletion is claimed by this report.

Reference checks used the [Cloudflare Workers best-practices documentation](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/) and [Resend's idempotency documentation](https://resend.com/docs/dashboard/emails/idempotency-keys). Resend documents a 24-hour deduplication window; the existing application stops uncertain retries earlier. The fixes preserve that boundary.
