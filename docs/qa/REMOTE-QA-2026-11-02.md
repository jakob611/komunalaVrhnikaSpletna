## Queue timing and controlled fixtures

The HTTP campaign endpoint starts background queue processing immediately. A one-recipient campaign can already be `complete` before the next request retracts the notice. Completion means the audience has been queued; delivery has its own status. In that observed case, the subsequent delivery was `failed/subscription_inactive` and no notification for that retracted notice reached the capture mailbox. Expecting the campaign itself to become cancelled after it had completed was an incorrect test assumption.

To exercise the pending cancellation branch deterministically, the test seeded **41 synthetic active road-topic subscribers through private QA D1 CLI**, using unique synthetic addresses and timestamps before campaign creation. These are test audience fixtures, not evidence of 41 public consent flows. Preview returned41; first bounded background batch left the campaign pending. The owner withdrew that notice, then invoked the real processing handler twice. The campaign became cancelled and no additional capture messages appeared after withdrawal. One synthetic message had already been accepted before withdrawal; the test does not claim it could be recalled.

Scheduled activation used an explicit, recorded QA-only fixture change: schedule `dc47030a-710f-46bb-978e-ab29bd03235d`, `cms_scheduled_publications.publish_on` changed from `2026-11-04` to `2026-11-02` by private CLI. The owner-only tick called the actual handler using real current time. This verifies due-work execution and publication; it does not claim a two-day wall-clock waiting test or an installed cron test. No production schedule was touched.
